# PRD 이후 만들기 절차 (prd-build)

PRD 한 장을 실제로 쓰는 도구로 만들 때까지의 순서다. 'PRD 이후 GitHub 기반 AI 개발 실행 가이드'의 1·4·5·6·7단계를 이 수업의 조건(클라우드 세션, 운영사 조직 레포, 배포 없음)에 맞게 줄였다.

## 1. 언제 쓰나

| 호출 | 하는 일 | 가이드 단계 |
|---|---|---|
| `/prd-build plan` | PRD를 요구사항·완료 기준·작업·검증 방법으로 나눈다 | 1 (팀은 2까지) |
| `/prd-build start` | 작업 하나(또는 이슈 #n)의 구현 순서와 확인 방법을 먼저 보여 준다 | 4 |
| `/prd-build step` | 다음 작은 단위를 구현 → 확인 → diff 확인 → 커밋·푸시한다 | 5 |
| `/prd-build review` | 변경 전체를 PRD 완료 기준으로 검토한다 | 6 |
| `/prd-build ship` | 병합 전 PR 본문 초안과 확인 목록을 만든다 | 7 |

## 2. 먼저 읽는 것과 모드

- 매번 먼저 읽는다: `CLAUDE.md`, PRD, 계획 파일(있으면), `docs/design.md`(팀, 있으면)
- **개인 모드:** `prd/m5_my_prd.md`가 있으면. 계획 = `docs/m5_plan.md`, 검토 = `checks/m5_check.md`, 커밋 머리 `[M5]`
- **팀 모드:** `prd/team_prd.md`가 있으면. 계획 = `docs/team_plan.md` + `docs/design.md` + `docs/issues_draft/`, 커밋 머리 `[팀-{역할}]`(통합·기능A·기능B·검증데이터) 또는 `[팀]`
- 둘 다 있거나 둘 다 없으면 어느 모드인지 사용자에게 한 번 묻는다.

## 3. 공통 규칙 (모든 호출)

1. 기존 파일과 사용자 변경을 덮어쓰지 않는다. `inputs/`와 `data/`의 원본 표본은 읽기만 한다.
2. PRD와 계획에 없는 기능, 이번 작업과 무관한 정리를 하지 않는다. 결과에 영향이 작은 선택은 이유 한 줄을 남기고 정한다.
3. 커밋·푸시는 묻지 않고 한다. **PR과 이슈는 초안 글만 쓴다** — 만들기·등록·리뷰 요청 전환·승인·병합은 사람이 한다(이 세션에서는 `gh pr`·`gh issue`가 동작하지 않는다).
4. main에 직접 푸시하지 않는다. 지금 세션 브랜치에만 푸시한다.
5. 실행하지 않은 확인은 "미실행"이라고 쓴다. 확인을 지우거나 기준을 낮춰서 통과시키지 않는다.
6. 개인정보·실제 업무 자료·외부 전송을 넣지 않는다. 데이터는 가상 표본만 쓴다.
7. 법규 적합·안전 판정·보상·계약금액·당첨·자격은 확정하지 않는다. "담당 검토 후 확정"으로 둔다.
8. 보고는 실제로 확인한 것만 한다: 바꾼 파일, 확인 결과, 커밋 메시지, 다음 할 일.

## 4. 호출별 절차

### plan — PRD를 작업 계획으로

1. PRD 3절(기능)에서 요구사항을 뽑아 번호를 붙인다(R1, R2 …). 개인은 MVP 1기능 = 요구사항 2~3개, 팀은 역할 ①~④에 맞춰 3~4개.
2. 요구사항마다 완료 기준을 쓴다: **성공**(어떤 입력에 어떤 결과) · **실패할 때 동작**(잘못된 입력에 어떻게 알리나) · **경계 조건**(빈 값, 단위 섞임, 중복 등). PRD 5절 성공 지표를 판정할 수 있는 문장으로 옮긴다.
3. 작업으로 나눈다. 작업마다 목적·포함/제외 범위·선행 작업·검증 방법·크기(S/M). 하나의 큰 작업보다 따로 확인할 수 있는 작은 작업을 고른다.
4. 대응표를 만든다: 요구사항 → 작업(팀은 이슈) → 검증 방법.
5. PRD에서 정해지지 않은 것은 **[가정]**으로 적고 계속한다. 만들기를 막는 질문만 마지막에 묶어서 묻는다.
6. 개인 모드: `data/m5_sample.csv`를 만든다(가상, 10~20행, 경계값 1개 이상, 일부러 넣은 함정 1개 — 어느 행이 함정인지 계획 4절에 적는다).
7. 팀 모드: `docs/design.md`(역할별 담당 파일·데이터 형식·화면이나 함수의 경계)와 `docs/issues_draft/1.md`~`4.md`(이슈 양식 칸: 목적·완료 기준·검증 방법·담당 파일·선행 이슈)를 만든다. 같은 파일을 두 역할이 고치지 않게 경계를 나눈다.
8. 계획 파일 끝에 **PR 본문 초안**(목적·범위·검증 계획)을 넣는다. 커밋·푸시한 뒤 "세션 화면 Create PR → 초안(Draft)으로 만들고 이 초안을 본문에 붙여 넣으세요"라고 안내한다.

### start — 작업 하나 시작

1. 대상 작업(개인 T1…, 팀은 이슈 #n과 `docs/issues_draft/`)과 PRD·계획·설계 메모를 읽는다.
2. 완료 기준과 **작은 구현 순서**(3~5단계, 단계마다 무엇으로 확인할지)를 보여 준다. 이때는 파일을 고치지 않는다(Plan 모드로 부르면 좋다).
3. 사용자가 승인하면 step으로 넘어간다.

### step — 작은 단위 하나

1. 이번 단위의 성공 조건과 고칠 파일을 한 줄로 밝힌다. 팀 모드는 `docs/design.md`의 담당 파일만 고친다.
2. 구현한다.
3. 확인한다: 개인은 `data/m5_sample.csv`로 완료 기준 해당 행을, 팀은 `tests/run_acceptance.py`(있으면)나 수용 기준표 해당 행을. 버그를 고칠 때는 가능하면 먼저 실패하는 경우를 재현한다.
4. 실패하면 원인을 고치고 다시 확인한다. 환경 때문에 못 한 확인은 "미실행"으로 남긴다.
5. diff를 보고 무관한 변경·디버그 출력·개인정보가 없는지 확인한다.
6. 이번 단위 파일만 커밋한다. 메시지 = 커밋 머리 + 작업 번호 + 한 줄(예: `[M5] T1 표본 불러오기·빈 값 표시`). 세션 브랜치에 푸시한다.
7. 보고: 커밋 메시지, 확인 결과, 다음 단위. 작업이 덜 끝났으면 같은 절차로 다음 단위를 제안한다.

### review — 완료 기준으로 자체 검토

1. 변경 전체를 PRD·계획의 완료 기준과 대조한다. 확인할 것: 결과가 맞는가, 실패·경계 입력에서 어떻게 되는가, 입력 확인, 개인정보, 범위 밖 변경, 빠진 확인.
2. 요구사항마다 **통과 / 실패 / 미검증**과 근거(실행한 확인, 표본 행)를 쓴다.
3. 발견 사항마다 심각도·위치·발생 조건·영향·고칠 방법을 쓴다.
4. 문서 맨 위에 **"AI 자체 검토 — 사람 리뷰 승인이 아님"**을 쓴다.
5. 개인 모드는 `checks/m5_check.md`로 저장·커밋한다. 팀 모드는 PR 본문에 붙일 검토 절로 보여 준다.
6. 고칠 것이 있으면 step 절차(수정 → 확인 → 커밋·푸시)로 처리하고 표를 갱신한다.

### ship — 병합 전 PR 본문

1. PR 본문 초안을 만든다: 목적 · 범위(한 것/안 한 것) · 검증 결과(통과·실패·미검증, 실행한 확인) · 미실행 확인 · 위험 · 되돌리는 방법(병합 뒤 Revert) · 팀은 첫 줄 `Closes #n`.
2. 개인 모드는 본문에 **"독립 리뷰 없음(1인 프로젝트) — AI 자체 검토 + 소유자 확인으로 대신함"**을 넣는다.
3. 사람이 할 일을 순서대로 안내한다: PR 본문에 붙여 넣기 → Ready for review 전환 → (팀) 리뷰 짝 지정·승인 → Files changed 확인 → Merge → main 확인.
4. 자기 PR을 승인하거나 병합하지 않는다. 승인 조건(팀: 조원 1명 승인, 리뷰 뒤 코드가 바뀌었으면 다시 승인)이 안 됐으면 병합하라고 하지 않는다.

## 5. 하지 않는 것

- PR·이슈를 직접 만들거나 병합하지 않는다(초안 글만).
- main에 푸시하지 않는다. 강제 푸시하지 않는다.
- 확인을 지우거나 기대값을 도구 결과로 바꿔 적지 않는다.
- 실제 업무 자료·개인정보·외부 주소를 쓰지 않는다.
- 계획에 없는 기능을 "하는 김에" 넣지 않는다.

## 6. 출력

| 모드 | 호출 | 파일 |
|---|---|---|
| 개인 | plan | `docs/m5_plan.md`, `data/m5_sample.csv` |
| 개인 | step | `tools/` 또는 `scripts/`의 `m5_*` |
| 개인 | review | `checks/m5_check.md` |
| 팀 | plan | `docs/team_plan.md`, `docs/design.md`, `docs/issues_draft/1~4.md` |
| 팀 | step | `docs/design.md`의 담당 파일, ④는 `data/team_sample.csv`·`tests/acceptance.md`·`tests/run_acceptance.py` |
| 둘 다 | ship | PR 본문 초안(채팅으로 보여 줌) |

계획·검토 파일의 칸은 레포의 양식(`docs/m5_plan.md`, `checks/m5_check.md`, `docs/team_plan.md`, `docs/design.md`)을 따른다. 양식이 있으면 칸을 채우고, 없으면 같은 칸으로 새로 만든다.

## 7. 예시

```text
/prd-build plan
/prd-build start T1
/prd-build step
/prd-build review
/prd-build ship
```

팀: `/prd-build start 이슈 #3` → `/prd-build step`(반복) → `/prd-build ship`
