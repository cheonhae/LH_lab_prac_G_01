# PRD — 민원 '적용 공고' 칸 자동 기재 도우미

| 항목 | 내용 |
|---|---|
| 결과물 형태 | HTML 파일 하나로 된 웹앱 — `tools/m5_notice_match.html`, GitHub Pages로 배포 |
| 입력 데이터 | 가상 표본 CSV 2개(민원대장, 공고 이력) — 화면에서 파일 선택 |
| 작성 | 2026. 11. 20.(금) · PRD 인터뷰(코어) 결과 |

## 1. 프로젝트 개요

- 해결하려는 문제: 민원대장의 '적용 공고' 칸에 어떤 공고를 적을지 담당자마다 판단이 다르다. 본공고·정정공고·변경공고가 겹쳐 있어서, 그중 어느 버전이 유효한지 고르기 어렵다.
- 배경: [가정] 정정·변경 공고가 자주 나오면서 담당자마다 기재 내용이 다른 일이 반복된다.
- 기대 변화: 담당자가 공고 버전을 직접 찾아 고른다. → 민원 접수일 기준으로 유효했던 공고가 자동으로 후보로 채워지고, 담당자는 검토만 한다.

## 2. 사용자 분석

- 주 사용자: 민원을 접수·처리하면서 '적용 공고' 칸을 채우는 실무 담당자.
- 사용 맥락: 주간·월간으로 민원대장을 정리할 때 여러 건을 한꺼번에 채운다.
- 현재 방식과 한계: 민원 건마다 게시판이나 공고 목록을 열어 하나씩 대조한다. 시간이 오래 걸리고, 그 사이에 나온 정정 공고를 놓치기 쉬우며, 유효한 버전 판단이 사람마다 다르다.

## 3. 기능 요구사항

- 핵심 기능(우선순위 순)
  1. **접수일 기준 자동 매칭** — 민원마다 같은 사업의 공고 중 접수일에 유효했던 버전을 골라 '적용 공고' 칸 후보를 채운다.
  2. 판단 근거 표시 — 왜 그 공고가 골라졌는지 보여 준다. (예: "정정 2차, 11/13 게시")
  3. '확인 필요' 표시 — 매칭이 안 되거나 판단 기준이 없는 건은 칸을 비우고 사유와 함께 담당자에게 넘긴다.
- 차별점: "최신 공고"가 아니라 "접수일에 유효했던 공고"를 고른다. 근거가 남아서 누가 처리해도 같은 결과가 나온다.
- 매칭 규칙 (2026-11-20 사용자 확정)
  - 사업명이 같은 공고 중 게시일이 접수일보다 앞선 버전에서 가장 늦은 것을 적용 공고로 한다.
  - 다음 경우에는 칸을 비우고 '확인 필요'로 표시한다.
    - 공고 이력에 사업이 없다.
    - 접수일 전에 게시된 공고가 없다.
    - 접수일과 같은 날 게시된 공고가 있다. 업무 기준이 정해지지 않아서다.
    - 날짜 형식을 읽을 수 없다.
  - 모든 결과의 상태는 "담당 검토 후 확정"이다. 도구가 확정하지 않는다.

## 4. 비기능 요구사항

- 사용 환경
  - 파일: `tools/m5_notice_match.html` 하나. PC 브라우저에서 열어 쓰고, 완성하면 GitHub Pages 주소로 배포한다.
  - 서버, 로그인, 설치, 외부 라이브러리, 외부 전송은 없다. 파일은 브라우저 안에서만 읽는다.
- 화면
  1. **파일 올리기** — 민원대장 CSV와 공고 이력 CSV를 각각 파일 선택으로 넣고 [매칭] 버튼을 누른다. 화면 위쪽에 "가상 표본만 넣으세요. 실제 민원 자료를 올리지 마세요" 안내를 둔다.
  2. **매칭 결과** — 민원마다 접수번호·접수일·사업명·적용 공고·근거·상태가 표 한 줄씩 보인다. 위쪽에 건수 요약(매칭 n건 / 확인 필요 n건)이 나온다.
  3. **저장·백업** — 마지막 결과를 브라우저에 저장하고, JSON 백업 파일로 내보내거나 가져온다.
- 입력(가상 표본만, 파일 선택)
  - 민원대장 CSV: `접수번호,접수일,사업명,민원요지`
  - 공고 이력 CSV: `사업명,공고구분,게시일` (공고구분 예: 본공고 / 정정 1차 / 변경 1차)
  - 날짜는 `YYYY-MM-DD` 형식으로 쓴다.
- 저장: localStorage 키 `m5_notice_match` 하나에 마지막으로 올린 공고 이력과 매칭 결과를 저장한다. [JSON 내보내기]·[JSON 가져오기]로 백업하고 되살린다.
- 데이터 민감도: 가상 표본만 쓴다. 배포 주소는 누구나 열 수 있으므로 실제 민원인 정보(이름·연락처·주소)는 넣지 않는다.
- 제약: 혼자, 45분 안에 만든다. 판단은 확정하지 않는다.

## 5. 성공 지표

- 성공 모습: 가상 민원대장과 공고 이력 파일을 고르면 3분 안에, 민원마다 접수일에 유효했던 공고 차수와 '확인 필요' 건을 화면에서 확인할 수 있다.
- 성공 시나리오(화면에서 판정)

  공고 이력 표본: 가상지구 A1 — 본공고 2026-10-01 / 정정 1차 2026-10-20 / 정정 2차 2026-11-13

  - **S1 정정 반영**: 접수일 2026-11-15인 가상지구 A1 민원을 넣으면 → 적용 공고 "정정 2차", 근거 "정정 2차, 2026-11-13 게시", 상태 "담당 검토 후 확정"이 보인다.
  - **S2 접수일 기준**: 접수일 2026-10-10인 가상지구 A1 민원을 넣으면 → 최신인 정정 2차가 아니라 적용 공고 "본공고", 근거 "접수일 당시 유효 — 정정 1차는 2026-10-20 게시"가 보인다.
  - **S3 확인 필요**: 공고 이력에 없는 사업명(가상지구 Z9)이 적힌 민원을 넣으면 → 적용 공고 칸은 비고, 상태 "확인 필요: 공고 이력에 해당 사업 없음"이 보인다.
- 참고 지표(표본으로 판정하지 않음): 실제 업무의 월간 대장 검수에서 정정 공고가 반영되지 않은 건 0건, 대장 정리 시간 감소.

## 6. 사용자 여정

1. 담당자가 배포 주소를 브라우저에서 연다.
2. 파일 올리기 화면에서 가상 민원대장 CSV와 공고 이력 CSV를 고르고 [매칭]을 누른다.
3. 매칭 결과 화면에서 적용 공고와 근거를 보고, '확인 필요' 건을 따로 검토한다.
4. 필요하면 저장·백업 화면에서 JSON으로 내보내 둔다.

## 7. 단계별 개발 우선순위

- MVP(이번): 기능 1 접수일 기준 자동 매칭. 결과 표의 적용 공고·한 줄 근거·상태 칸, 3절 매칭 규칙의 '확인 필요' 판정, 저장·백업까지 포함한다.
- 다음
  - 기능 2 확장: 사업별 공고 버전 타임라인 등 상세 근거
  - 기능 3 확장: '확인 필요' 사유별 분류와 모아 보기
  - 결과를 CSV로 내려받기
  - 붙여 넣기 입력
- 추후: 접수일과 게시일이 같은 날인 경우의 업무 기준 반영, 변경 공고와 정정 공고의 우선 규칙.

## 8. 수용 기준

| # | 기준 | 확인 방법 | 결과 |
|---|---|---|---|
| AC1 | S1~S3이 5절대로 화면에 보인다 | 표본 CSV를 넣고 결과 표 확인 | ☐ 통과 ☐ 수정 |
| AC2 | 모든 결과 상태가 "담당 검토 후 확정" 또는 "확인 필요: 사유"이다 | 결과 표 상태 칸 확인 | ☐ 통과 ☐ 수정 |
| AC3 | 외부 라이브러리·외부 요청이 없다 | HTML의 `<script src>`·`fetch` 검색, 개발자 도구 네트워크 탭 확인 | ☐ 통과 ☐ 수정 |
| AC4 | 저장 키가 `m5_notice_match` 하나이고, JSON 내보내기 → 가져오기 후 같은 결과가 보인다 | 개발자 도구 Application 탭, 백업 되살리기 | ☐ 통과 ☐ 수정 |
| AC5 | 실제 자료 금지 안내가 첫 화면에 보인다 | 화면 확인 | ☐ 통과 ☐ 수정 |

## 9. 위험 요소

- "최신 공고"를 고르게 잘못 만들면 S2가 틀린다. 접수일 비교를 빠뜨리기 쉽다.
- 사업명 표기가 조금만 달라도(띄어쓰기 등) 매칭되지 않는다. MVP에서는 '확인 필요'로 넘기고, 짐작으로 맞추지 않는다.
- 배포 주소가 공개라서 실제 자료를 올리면 안 된다. 파일은 브라우저 밖으로 나가지 않지만 안내로 한 번 더 막는다.

## 10. 판단 경계

- 이 도구는 적용 공고를 확정하지 않는다. 화면의 모든 결과는 "담당 검토 후 확정"이며, 최종 기재는 담당자가 한다.
